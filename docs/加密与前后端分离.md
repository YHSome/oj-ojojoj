# 前后端分离 + 非对称加密链路（OJ-OJOJOJ v2）

> 前端：**纯静态 HTML + CSS + JS**（`frontend/`，无框架、无构建、无依赖）
> 后端：**本机判题机**（`backend/`，`D:\OJ`）
> 中转：**云端 TinyWebDB**（前端与后端都只通过它通信，彼此不知道对方的存在）

---

## 1. 为什么这样拆

| 角色 | 职责 | 依赖 |
|---|---|---|
| 前端 `frontend/` | 界面、加解密、读写标签 | 只要浏览器 + 云端 API 可达（`Access-Control-Allow-Origin: *`，可直连） |
| 后端 `daemon.py` | 轮询队列、解密、编译判题、写回结果 | 只要云端 API 可达 + 本机工具链 |
| 云端 KV | 消息总线 + 存储 | 无 |

两者**没有任何直连**：前端不需要知道判题机在哪台机器、什么 IP、什么端口；
判题机也不需要对外开端口。唯一的耦合是标签契约（`docs/PROTOCOL.md`）。

## 2. 一次加密提交的完整时序

```
前端(浏览器)                          云端 TinyWebDB                    后端(判题机, 3s 轮询)
    │                                       │                                 │
    │ ① get oj:pubkey ─────────────────────►│                                 │
    │ ◄──────────── RSA 公钥(JWK) ──────────│                                 │
    │                                       │                                 │
    │ ② crypto.subtle RSA-OAEP(SHA-256) 分块加密源码（每块 ≤190B）             │
    │                                       │                                 │
    │ ③ update code:<SID>:0..k ────────────►│  (密文分片, base64url)           │
    │    update code:<SID> (清单) ─────────►│  {alg,enc,n,sha256,to,state}     │
    │    update sub:<SID> (含 client_pubkey)►│                                 │
    │    update q:<SID> ───────────────────►│  ← 队列                          │
    │                                       │ ◄── ④ search q: (每 3 秒) ───────│
    │                                       │ ◄── ⑤ get code:<SID> + 分片 ─────│
    │                                       │         私钥解密 → 内存           │
    │                                       │ ◄── ⑥ update code:<SID> ─────────│  改成 {"state":"judging"}
    │                                       │ ◄── ⑦ delete code:<SID>:i ───────│  密文分片全部清除
    │                                       │                                 │ ⑧ 编译 + 逐点判题
    │                                       │ ◄── ⑨ update res:<SID>:i ────────│  结果密文(客户端公钥)
    │                                       │ ◄── ⑩ update res:<SID> ──────────│  清单 + 判题机签名
    │                                       │ ◄── update sub:<SID> 终态 ───────│  verdict/score
    │ ⑪ get sub:<SID> (轮询) ───────────────►│                                 │
    │ ⑫ get res:<SID> + res:<SID>:i ────────►│                                 │
    │ ⑬ 私钥解密 + 用 oj:pubkey 验签 → 展示   │                                 │
```

对应代码位置：

| 步骤 | 前端 | 后端 |
|---|---|---|
| ① | `app.js: refreshJudgeKey()` | `daemon.py: _setup_crypto()` → `store.publish_pubkey()` |
| ②③ | `app.js: doSubmit()` + `crypto.js: seal()` | — |
| ④⑤⑥⑦ | — | `daemon.py: fill_queue()/do_judge()` → `store.take_submission_code()` |
| ⑧ | — | `judge.py: judge_submission()` |
| ⑨⑩ | — | `store.finish()/seal_result()` |
| ⑪⑫⑬ | `app.js: pollOnce()` + `crypto.js: openSealed()/verifySignature()` | — |

## 3. 密码学细节（前后端严格一致，且已互测）

| 项 | 取值 |
|---|---|
| 算法 | **RSA-OAEP**，SHA-256（浏览器 `{name:"RSA-OAEP", hash:"SHA-256"}`） |
| 密钥 | 2048 位；后端启动时生成/加载 `data/state/judge_key.json`（JWK 格式） |
| 公钥发布 | `oj:pubkey` = `{kty,alg,use,n,e,fingerprint}`，前端 `importKey('jwk', ...)` 直接用 |
| 分块 | 每块明文 ≤ `k - 2*hLen - 2` = **190 字节**，任意长度数据按块加密 |
| 密文编码 | base64url（无 `+ / =`），通过安全文本层写入 KV |
| 数据完整性 | 信封带 `sha256`（明文摘要），解密后校验 |
| 结果回传 | 用**客户端公钥**加密；客户端会话内自生成密钥对 |
| 结果签名 | 判题机私钥 **RSASSA-PKCS1-v1_5(SHA-256)**，前端用 `oj:pubkey` 验签 |

为什么不用对称加密（AES）+ 封装密钥：本项目**没有 `cryptography` 依赖**，
后端用纯标准库实现 RSA（`pow()` 模幂足够快，实测 5000 字节加解密 0.16 秒），
纯非对称链路让"代码加密"这件事在前后端只依赖一个算法，能逐字节互测。

### 实测性能（本机）

| 数据量 | RSA 块数 | 加密+解密耗时 |
|---|---|---|
| 128 字节（典型 A+B 代码） | 1 | ~5 ms |
| 5000 字节 | 27 | ~160 ms |
| 20000 字节（约 600 行） | 106 | ~600 ms |

## 4. 云端 KV 的硬约束（v2 新增实测项）

| # | 实测结论 | 对策 |
|---|---|---|
| 13 | **单值 10000 字符可用，20000 字符会被服务端破坏**（读回只剩 4 字符） | 所有长内容按 **8000 字符/标签**分片：`code:<SID>:i`、`res:<SID>:i` |
| 14 | **`delete` 是软删除**：`search`/`count` 里消失，但 `get` 会返回字符串 `"null"` | 客户端统一把字面量 `"null"` 当作"不存在"（`twdb.get` / `tinywebdb.js: getRaw`） |
| 15 | 官方 API 返回 **`Access-Control-Allow-Origin: *`** | 纯静态前端可以浏览器直连；但**不能加自定义请求头**（会触发预检且服务端没有 `Allow-Headers`），只能用 `application/x-www-form-urlencoded` 简单请求 |
| 16 | 同机起两个判题机实例 → 同一个 `judge_id` → 双方都能"抢到"同一提交 | 启动时写 `data/state/daemon.lock`（PID + 存活检测）**硬拦第二个实例**；多实例必须 `--allow-multi` 且各自不同 `judge.id` |

> 第 16 条是真实踩到的坑：两个实例同时判同一个提交，一个拿到的 `code:` 已经是
> "判题中"标记（于是把标记当源码编译，判成 CE），另一个正常判成 AC，
> 最终结果被 CE 覆盖。加锁后不再复现。

## 5. 安全边界（诚实说明）

**做到了**：
* 源码在云端只以密文存在；判题机取码后立即删除密文分片并把标签改成「判题中」。
* 结果用提交者公钥加密回传，别人（含其他参赛者、云端管理员）读到的只有 `verdict/score` 摘要。
* 结果附判题机签名，前端验签，防伪造。
* 账号密码只存 `sha256(salt:pass)`，登录走命令总线由后端算哈希。

**没做到（不要误解）**：
* 前端页面本身是静态文件，无 TLS 时页面可能被篡改（页面被改就能偷密钥）。正式部署请上 HTTPS。
* 客户端私钥在 `sessionStorage`，同一浏览器会话可用；不做前向保密。
* 判题机不暴露端口、不进你家网络，但它自己跑在 Windows 上，隔离强度有限（见 ARCHITECTURE §8）。
* 云端是公共免费服务：**不要放敏感数据**，本项目只放密文与摘要。
