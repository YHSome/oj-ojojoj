# 多机共判（Multi-Judge）通讯方案

> 目标：**多台评测机同时接单、压力均摊、互不重复判、任一台挂掉任务不丢**。
> 约束：云端 TinyWebDB 只有 `update/get/delete/count/search`，**没有 CAS、没有事务、没有原子自增**，
> `search` 单次上限 100 条且返回无序，服务端还会 503 限流。
> 所以整套方案是"**弱一致 KV 上的租约 + 概率分摊**"，而不是分布式锁。

---

## 1. 总体结构

```
                      ┌──────────────── 云端 TinyWebDB（唯一的共享介质）────────────────┐
                      │  q:<SID>      待判队列（判完/认领即删，有界小集合）             │
                      │  sub:<SID>    提交记录：status / judge / lease_token / attempt │
                      │  judge:<ID>   判题机心跳：workers,busy,free,load,langs,share   │
                      │  res:/code:/… 结果与源码                                       │
                      └───────────────────────────────────────────────────────────────┘
                              ▲  轮询(3s)   │  写租约/心跳/结果
        ┌─────────────────────┼─────────────┼─────────────────────┐
        │                     │             │                     │
   ┌────┴─────┐          ┌────┴─────┐  ┌────┴─────┐          ┌────┴─────┐
   │ JUDGE-A  │          │ JUDGE-B  │  │ JUDGE-C  │   ...    │ JUDGE-N  │
   │ 4 worker │          │ 4 worker │  │ 8 worker │          │ 2 worker │
   └──────────┘          └──────────┘  └──────────┘          └──────────┘
```

**没有任何机器直连任何机器**，全部通过云端标签交换信息。任何一台随时上下线都不影响别人。

---

## 2. 任务生命周期与"谁抢到"的判定

```
前端写 q:<SID> ──► 所有判题机每 3s 拉一次 q:（无序，按 ts 本地排序）
                        │
                  ①能力过滤：自己没这个语言的工具链 → 直接跳过（留给有能力的机器）
                        │
                  ②概率过滤：p = 我的空闲权重 / 集群空闲权重 → 按 p 决定要不要接
                        │
                  ③认领（乐观租约）：
                       a. 读 sub:<SID> 看 status/lease_until
                       b. 一次性写入 {status:judging, judge:me, lease_token:随机, lease_until:now+TTL}
                       c. 抖动 sleep 150~400ms（打散并发窗口）
                       d. 回读：lease_token == 我的 → 认领成功；否则放弃（对手赢了）
                        │
                  ④认领成功立刻 delete q:<SID>（让别的机器下一轮看不到，减少争抢）
                        │
                  ⑤判题（编译→逐点跑）；期间每 0.4×TTL 续租一次（长任务不会被误抢）
                        │
                  ⑥写结果前**再校验一次租约**：不是我的就丢弃本次结果（陈旧结果丢弃）
                        │
                  ⑦写 res:<SID>、翻 sub:<SID> 终态、释放租约
```

### 为什么这样就"不会判错"

无 CAS 的 KV 上，**两个人可能同时认为自己抢到了**（A 写入后回读发生在 B 写入之前）。
本方案的处理是：

| 环节 | 保证 |
|---|---|
| 认领回读 | 把并发窗口压缩到"后写者赢"，抖动后绝大多数情况只有一个赢家 |
| **写结果前校验租约** | 即使两个人都判了，**只有租约仍然有效的那个人能写结果**，另一个的结果被丢弃 |
| 结果内容确定性 | 同一份代码 + 同一份测试数据 → 结果一致；最坏情况是"多花一份 CPU"，绝不会写错判定 |

> 这正是 MiniJudge 的 lease-v1 思路：**宁可重复计算，不可重复写入**。

## 3. 均摊算法（核心）

每台机器在心跳里发布自己的余力：

```json
judge:JUDGE-A = {
  "id":"JUDGE-A", "host":"PC-A", "workers":4, "busy":1, "free":3,
  "load_pct":35,          // CPU 利用率（Windows GetSystemTimes / Linux /proc/stat 采样）
  "langs":["c","cpp","py"], "queue":2, "share":0.62,
  "share_mode":"auto", "paused":false, "stats":{"judged":41,"ac":30}, "ts":1730000000
}
```

每台机器算出自己应该接的比例：

```
penalty      = max(0.15, 1 - cpu_load)            # CPU 越忙越少接，但有下限
my_weight    = free_slots × penalty               # 我就这么大能力
others       = Σ(同伴的 free_slots × penalty)      # 同伴总能力
p            = my_weight / (my_weight + others)   # 期望上：按能力比例分单
p            = max(claim_min_prob, min(1, p))     # 下限 0.08，防止弱小机器被饿死
```

* 只有一台在线时 `p = 1.0` → **退化成单机行为，不影响现有部署**；
* 4 核机器与 16 核机器同场：后者 `p ≈ 0.8`，前者 `≈ 0.2`，按真实能力分摊；
* 某台机器正在跑 4 个 TLE 任务（`free=0`）→ `p → 下限`，任务自然流向空闲机器；
* 结果：**负载是"按余力概率接单"实现的软均摊**，不需要中央调度器，也不需要谁当 leader。

### 为什么用概率而不是"分片（sharding）"

| 方案 | 问题 |
|---|---|
| 按 SID 哈希分片 | 机器上下线要重新分片（KV 上没法原子改配置）；某台挂了它的分片就积压 |
| 中央调度器指派 | 需要额外常驻服务 + 它的可用性成为瓶颈；违背"只有 KV"的架构 |
| **概率接单 + 租约兜底** | 无中心、动态成员自适应、挂了任务自然被同伴捡走；代价是偶尔重复认领（已被租约挡住写结果） |

## 4. 容错

| 故障 | 现象 | 处理 |
|---|---|---|
| 判题机中途崩溃 | `status=judging` 但没人再动它 | 租约 TTL（默认 180s）到期后，任何机器扫到都会把它按 **JE + attempt+1** 重新入队（`recover_stale`） |
| 判题机重启 | 自己的残留租约还占着 | 启动时先 `expire_own_leases()` 作废自己的旧租约，再 `recover_stale()` |
| 任务反复失败 | attempt 涨到上限 | `limits.retry_max_attempts`（默认 3）之后判终态 `JE`，不再无限重试 |
| 语言工具链缺失 | 有的机器只会 Python | 认领前的**能力过滤**：`sub.lang` 不在自己的 `available_langs()` 里就不接，留给有 g++ 的机器 |
| 长任务被判超时抢走 | TLE 重的题跑很久 | 判题期间按 `lease_renew_ratio`（0.4×TTL）**持续续租**，`renew_lease` 失败即放弃本次结果 |
| 时钟不同步 | 租约判定错乱 | 判题机之间只比较"相对时长 + 一个宽限"，建议各机 NTP；跨机时间差 > 30s 会在控制台告警（见 §6） |
| 云端 503 限流 | 拉取失败 | 指数退避；多机轮询时**每台的间隔带抖动**，避免同一秒撞在一起 |

## 5. 云端请求预算（多机情况下必须算的账）

单机基线：拉队列 1 次/3s + 命令总线 1 次/3s + 心跳 1 次/20s ≈ **0.8 次/秒**。
判一个提交 ≈ 8 次请求（取 sub、认领 2、取码、续租若干、写 res/sub/删 q）。

| 判题机数 | 空闲时请求量 | 结论 |
|---|---|---|
| 1 台 | ~0.8/s | 安全 |
| 3 台 | ~2.4/s | 尚可，遇 503 会自动退避 |
| 5 台+ | ~4/s | **需要拉长间隔**（见下） |

缓解手段（都已实现或可调）：

1. **认领即出队**：任务一旦被认领就从 `q:` 消失，其他机器下轮拉不到 → 争抢请求量下降；
2. **集群感知的轮询退避**：`_refresh_share()` 每 5s 才读一次集群视图（不是每轮）；
3. 心跳间隔可调（`judge.heartbeat_interval_s`），机器越多可以调大；
4. `sub:` 全表兜底扫描默认只有 10% 概率触发，多机时可再降；
5. 极端情况：给每台机器设不同的 `queue_refresh_interval_s`（例如 3/4/5 秒错峰），
   或用 `judge.share_mode=greedy` 只让主力机抢、其余机 `solo` 只处理指定语言。

## 6. 可观测性（中控台）

* 每台机器的 `judge:<ID>` 心跳本身就是"在线列表"：`search tag=judge:` 即得集群视图；
* `cluster_summary()` 汇总：台数 / 总 worker / 空闲 / 语言并集；
* 每条提交的 `sub.judge` 记录了**是谁判的**，`sub.attempt` 记录**被认领过几次**
  （>1 说明发生过争抢，正常但应很少）；
* 控制台可看：各机 free/workers、CPU、分单比例 `share`、已判数量、队列深度；
* 排查"任务没人判"：看 `q:` 里还有谁没被领走，以及是否有机器支持那个语言。

## 7. 上线成本（新增一台判题机）

```bash
# 1) 拷一份仓库到新机器（或用 bundle / zip）
python tools/get_repo_zip.py --extract        # 或 git clone

# 2) 填同一个云端实例（config/oj_config.local.json）
#    只要 api.user/secret 与主站一致，就自动连着同一个队列

# 3) 起判题机，给它一个唯一 ID（多机必须唯一！）
python backend/daemon.py --workers 4 --set judge.id=JUDGE-PC2

# 4) 中枢机上确认它上线
python - <<'EOF' ... cluster_summary() ... EOF   # 或在中控台看"集群"面板
```

**注意**：`judge.id` 是唯一身份标识，重复 ID 会让两台机器互相认为对方是自己
（单机启动有 `daemon.lock` 兜底，跨机必须人工保证唯一）。

## 8. 参数速查

| 参数 | 默认 | 说明 |
|---|---|---|
| `judge.share_mode` | `auto` | `auto` 按余力概率分摊；`greedy` 能抢就抢（主力机）；`solo` 独占（只处理指定语言） |
| `judge.claim_min_prob` | 0.08 | 单机最低分单比例，防止慢机被饿死 |
| `judge.cluster_ttl_s` | 45 | 判定"同伴在线"的心跳有效期 |
| `judge.cluster_cache_s` | 5.0 | 集群视图本地缓存，减少云端请求 |
| `judge.lease_seconds` | 180 | 任务租约时长（超时视为失联） |
| `judge.lease_renew_ratio` | 0.4 | 长任务续租间隔 = 该比例 × 租约时长 |
| `judge.heartbeat_interval_s` | 20 | 心跳间隔（机器多时可调大） |
| `limits.retry_max_attempts` | 3 | 判题机侧故障（JE）最大重试次数 |
| `judge.lock_jitter_ms` | [150,400] | 认领抖动，打散并发窗口 |
